# Java RGI: аудит состояния на 2026-09-13

Проверена ревизия `dda63e440a31290361dee99e0d78a5f1a32c388e` (`master`).
Ниже сохранены результаты аудита этой ревизии. После команды пользователя
исправления реализованы в рабочем дереве; их статус приведён отдельно.
Чужие изменения audio/UI не входят в проверку. Проверки выполнялись на хосте;
новых наблюдений на физическом HUD/VC или развёртывания на машине нет.

**Уточнение после проверки полного CarPlay → BAP пути:** наследование старого
exit angle не воспроизводится со штатным C-producer: `rgd_tlv.c:618–620`
всегда публикует `1000` для индексированного манёвра без угла. Первоначальный
Java-only пример обходил эту защиту. Наследование других отсутствующих полей
подтверждено и через C → Java → BAP. Выбор HUD-иконок не регрессировал:
7 890 случаев совпали с прежним кодом, как и 1 083 полноценных lane-записи.
См. [отдельную проверку HUD](CARPLAY_HUD_REGRESSION_CROSSCHECK_2026_09_13.md).

## Исправления после аудита

Все четыре воспроизведённые проблемы закрыты в рабочем дереве:

1. Очередь объединяет прогресс только внутри одного манёвра, защищает
   принятые манёвры и CLEAR. При заполнении критическими командами возвращает
   отказ и запускает повтор общего RGI-состояния. Живое соединение при этом
   не разрывается. Прогресс и blink нового манёвра не отправляются на старую
   стрелку до принятия команды геометрии.
2. Dirty-флаги сохраняются до успешной публикации обоих выходов, в том числе
   при следующем distance-only delta. Работник повторяет публикацию с паузой,
   даже если iOS больше не присылает пакеты. Уже действующий контекст остаётся
   видимым при временной ошибке; первоначальное подтверждение ждёт успешной
   публикации. Повтор принятой геометрии не запускает ещё один переход.
3. Смена `mN_ver` очищает поля прежнего владельца до разбора новых данных.
   Отдельные lane events этим не удаляются. Новый ключ C → Java
   `route_generation` различает сбросы native-кэша с повторяющимися версиями;
   новое поколение удаляет устаревшие данные маршрута и полос.
4. Возраст относительного времени хранится в `RouteGuidance.State` и
   сохраняется при повторе. Неизменённое значение в полном cached snapshot
   C-хука не считается новым замером.

HUD и renderer используют одно актуальное RGI-состояние, общие целевые
значения прогресса и один источник фаз мигания. Renderer самостоятельно
анимирует заполнение, догон цели и откат при переходе между манёврами.
Транспорты асинхронны: это восстановление согласованного
состояния, а не гарантия физически одновременного кадра на двух экранах.
Очередь подтверждает приём команды, а не её показ на дисплее.

Проверки:

- `scripts/test_route_info.sh`: штатные проверки плюс настоящие parser,
  `onFrame`, BAPBridge и retry-worker с подставными отказами выходов;
  холодный старт, длительный отказ, последующая дистанция, смена манёвра,
  hide полос, обе blink-фазы, возраст времени и отсутствие повторного проезда.
- `scripts/test_java_transports.sh`: реальные сокеты, порядок CLEAR/манёвров,
  давление прогрессом, полная очередь и остановка старых writer-потоков.
- `tests/test_rgd_native_contract.py`: настоящий C TLV parser, извлечённые
  без изменения reset/slot writer/text builder, затем Java и stock BAP sender;
  C-часть с ASan/UBSan. Новый слот даёт те же sideStreets, что свежий кэш.
- Повтор `ManeuverChainAudit`: 7 890 строк, 0 отличий от `07e980d`.
  Lane lifecycle matrix: 1 083 случая и отдельные sentinel-проверки.
- `scripts/check_local_protocols.py`: 38 констант совпадают, 107 shipping
  классов Java 1.4. Изменённый `rgd_hook.c` отдельно скомпилирован штатными
  build-флагами в QNX/ARM toolchain; весь audio-код заново не собирался.

Для защиты от native reset с повтором версий нужны обновлённые hook и JAR
вместе. Старый hook не передаёт поколение маршрута. Развёртывание на ГУ и
проверка на физическом HUD в этот проход не выполнялись.

## Подтверждённые проблемы исходной ревизии

### 1. P1 — новый манёвр теряется при переполнении очереди renderer

`RendererServer.sendPacket`, строки 674–695: очередь из 32 записей защищает
CLEAR, последний viewport и последний пакет полос. CMD_MANEUVER считается
обычной записью и может быть удалён последующими CMD_PROGRESS.

`BAPBridge.updateRendererIfChanged`, строки 2056–2058 и 2095–2110: после
успешной постановки в очередь геометрия и идентификатор манёвра считаются
отправленными. Повтор того же манёвра отсекается, даже если очередь его уже
выбросила. Комментарий «ordinary state can be resent» не обеспечивает повтор.

Воспроизведение настоящими BAPBridge/RendererServer без запуска writer:
принять один манёвр, затем 80 обновлений заливки. В очереди остаётся **0
манёвров**, а повторный вызов с тем же манёвром возвращает false. Это модель
задержанного writer/сокета; частота возникновения на ГУ не измерялась.
Последствие — старая стрелка с прогрессом нового манёвра либо пустая сцена
после CLEAR.

Исправление должно сохранять последнее требуемое состояние манёвра и порядок
относительно CLEAR. Сначала стоит объединять устаревшие обновления прогресса.
Нельзя просто пометить ещё один вид пакета защищённым и забыть про повтор при
полностью занятой очереди: enqueue-failure также должен будить восстановление.
`updateRendererIfChanged` сейчас возвращает false и для «не изменился», и для
«не отправлен», а `BAPBridge.update` эти случаи не различает.

### 2. P1 — ошибка BAP после запуска теряет обновление без повтора

`RouteGuidance.onFrame`, строки 554–570: если представление уже подтверждено
и renderer остаётся готов, `bap.update(state) == false` сохраняет
`presentationConfirmed == true`. Это правильно для отсутствия мигания
контекста, но затем `clearDirty()` удаляет признаки недоставленного обновления,
а повтор назначается только при `!confirmed`.

Воспроизведение через настоящий `BAPBridge.update`: подставной HUD выбрасывает
исключение при скрытии полос, после чего `published=false`, `dirtyMask=0`,
`presentationDrivePending=false`, `presentationConfirmed=true`. Последующие
пакеты с тем же содержимым не становятся dirty. Ранняя ошибка BAP также
прерывает отправку renderer, которая расположена ниже в этом же методе.

Нужны отдельные признаки «представление можно показывать» и «всё требуемое
состояние доставлено». Повтор должен запускаться при ошибке публикации,
сохраняя действующий контекст при живом renderer. Проверить и
`driveCachedPresentation`: его текущая проверка `published && ready` иначе
снова начнёт скрывать контекст при неудачном повторе.

### 3. P1 — новый манёвр наследует отсутствующие поля старого слота

`RouteGuidance.parse`, строки 1042–1195: поля читаются как delta.
Обработка `mN_ver` в строках 1140–1147 только обновляет версию и dirty-флаги,
но не очищает данные предыдущего владельца слота. В штатной цепочке проблема
касается отсутствующих боковых дорог, названия, длины участка и других полей;
exit angle отдельно защищён C-парсером и не наследуется.

Это совместимо с реальным producer, а не только с искусственным пакетом:
`hook/routeguidance/rgd_hook.c`, `rgd_slot_for_iap_index` (331–380) назначает
нового владельца и очищает native-кэш; `write_slot_data_keys` (478–590)
передаёт только присутствующие поля. Для отсутствующего exit angle C-парсер
заранее выставляет значение 1000 и present-бит, поэтому writer публикует его
явно. Общей очистки других отсутствующих полей манёвра нет. В отличие от
этого, lane-кэш имеет отдельные clear-ключи и
очищается в Java при смене `lgN_index`.

Уточнённое воспроизведение через настоящий C TLV parser, неизменённый slot
writer, Java parser и BAP sender: старый слот имеет дороги `[-90,0,90]`,
`Old road` и длину 6000 м. Новый правый поворот с известным углом +90°, но без
этих необязательных полей сохраняет старые значения. BAP sideStreets для него
равен `[64,0]` после повторного использования слота и `[]` для свежего слота.
Если у нового манёвра нет угла, Java корректно получает 1000 и HUD sideStreets
остаётся пустым. Следовательно, первоначальный пример старого угла нужно
считать проверкой Java в изоляции, а не доказательством ошибки штатного входа.

Есть второй случай: `rgd_maneuver_map_reset` обнуляет счётчик версий, а Java
сохраняет слоты на `route_state=0`. Более того, native reset может происходить
во время debounce до передачи нуля в Java (строки 1396–1401). Поэтому только
проверки `mN_ver` недостаточно для нового маршрута: версия может совпасть с
прошлым маршрутом.

Нужен явный контракт идентичности: reset слота **до** применения полей нового
владельца плюс поколение маршрута или версия, не повторяющаяся при native
reset. Нельзя решать это безусловным удалением кэша на любом кратковременном
нуле iOS — кэш нужен для данных, которые телефон повторно не присылает.

### 4. P2 — повтор кэша возвращает старое оставшееся время

`RouteGuidance.State.markAllDirtyForReplay` (290–299) включает
DIRTY_TIME_REMAINING. `BAPBridge.cacheTravelInfo` (1312–1323) трактует это как
новый замер и устанавливает время получения в «сейчас».

Если абсолютной ETA нет, оставшееся время считается по длительности и
прошедшему времени. Воспроизведение: длительность 600 секунд, замер 120
секунд назад → 480 секунд; повтор того же кэша → снова 600 секунд. При
валидной абсолютной ETA этот конкретный эффект отсутствует.

Время получения должно принадлежать исходному RGI-состоянию. Повтор
представления должен сохранять возраст замера.

## Что Java сейчас действительно делает

| Участок | Назначение / текущая политика |
| --- | --- |
| `CarplayBus → RouteGuidance` | Разбор delta, 32 слота манёвров и отдельный кэш lane events; start/stop, очистки, dirty-флаги, повтор при готовности сервисов. |
| `ManeuverMapper + SideStreets` | Перевод типов/углов CarPlay в семейства и направления BAP, квантование дорог для HUD, правила driving side и sentinel. |
| `BAPBridge` | Отправка в штатный AppConnectorNavi, расстояния, prepare/action/blink, текст, ETA, выбор активного lane event, координация renderer. Это 2475 строк с несколькими обязанностями. |
| `RendererMapper` | Общее с HUD семейство манёвра + допустимая сырая геометрия CarPlay. Полосы не участвуют в выборе формы манёвра. |
| `RendererServer` | TCP, команды по 48 байт, атомарные снимки полос, очередь, READY/FRAME_READY/CLEAR ACK, reconnect, viewport. |
| `RgdModule / CarPlayApp` | Порядок запуска, получение Navigation service, повтор старта, перепривязка при смене OSGi service. |
| `GatedCombiService / AltScreenNavStatusGate / ClusterService` | Владение BAP во время CarPlay и блокировка конкурирующих штатных обновлений; восстановление на штатном NavigationJobs. |
| `AltScreenModule / ClusterLayerController / DisplayManager / CombiMapController` | Контексты 80/81, отдельный renderer displayable 98, реальная геометрия viewport, stock layout и управление видимостью. |
| `SteeringWheelInputModule` | Переключение текста маршрута/времени кнопкой OK, только при соответствующем контексте RGI. |

Геометрия дорог, материалы, камера, движение между манёврами, интерполяция
заливки, тени, нижняя строка полос и маска принадлежат native C/C++ engine.
Старой Java-логики выбора primary lane, вывода топологии многополосной дороги
или подстановки формы манёвра по полосам в текущей цепочке нет.

Существенные ручные политики, которые ещё есть и меняют представление:

- Реальный манёвр виден на любой дистанции. Java вычисляет prepare/action по
  расстоянию: город 1500 м, highway 3000 м; участок длиннее 2000 м считается
  highway. Action использует длину участка, ограниченную 15% prepare-порога
  (225/450 м); при неизвестной длине берётся этот предел;
  blink — последние 20% action-zone, фаза 600 мс. Это наши эвристики, а не
  буквальное воспроизведение присланного `maneuver_state`.
- Ramps отображаются одним slight turn. Для off-ramp добавлена продолжающаяся
  прямо дорога. Это принятый выбор формы, не остаток lane-road эксперимента.
- Renderer сохраняет полный круг и допустимые непрерывные sharp-углы, хотя
  HUD имеет дискретный каталог. Противоречащий типу знак угла не побеждает тип.
- Полосы выбираются по активному lane event и `lane_guidance_showing`.
  Они могут появляться и исчезать внутри одного манёвра. Не зависят от
  prepare-distance и не обязаны принадлежать самому maneuver descriptor.
- Основной текст идёт в FctID 19, FctID 20 очищается. Кнопка OK переключает
  текст/время. FctID 22 остаётся абсолютным временем прибытия.

## Что сохранить и что можно упростить

Сохранить явные защиты `1000 / -1000`, отдельный признак присутствия для
реального угла −1°, правила конфликтующих углов, полный круг, ramp/slight,
версию манёвра, refresh-only обновления и общую фазу HUD/renderer blink.
Lane-пакеты сохраняют raw sentinel; HUD-конвертер явно возвращает `0xFF`
для обоих sentinel. Штатные проверки этих случаев проходят.

Не удалять как «костыль» переключение ExitView EU/NAR с номером 0: оно
обеспечивает штатную FSG-синхронизацию FctID 23/18/49. Также нужны
presentation gate, OSGi rebind и workaround доступа к BAPDistanceFormatter
при сборке против реконструированного stock JAR.

Кандидаты на небольшую отдельную чистку:

- `lastDistanceToDestinationM` только записывается и сбрасывается; чтений нет.
- `hexBytes` не вызывается.
- Перегрузка `mapRawLaneValueToDirectionCode(raw, excludeOneNativeKey,
  keyToExclude)` вызывается только с `false, 0`; параметр исключения не нужен.
- Комментарии всё ещё упоминают respawn из Java, displayable 20,
  приоритет `visible_in_app=0` и transient route-zero, хотя текущий путь иной.
- `keepLastColonPart` у `mAfterRoad` отрезает всё до последнего `:`. На
  структурированной строке bus это может обрезать настоящее название.
  Отдельное предположение о происхождении старого обхода не подтверждено;
  автоматическое обрезание требует явного обоснования/теста входного формата.
- `CarplayBus.Data.intList` заменяет ошибочный числовой токен на `0`.
  Для RGI углов это реальное «прямо», а для списка — слот 0. Native producer
  пишет числа сам, поэтому нормальный сценарий с таким повреждением не
  установлен. При усилении парсера нужен RGI-specific invalid, с сохранением
  позиции элементов и различием missing/empty/invalid.
- Legacy `mN_lane_*` fallback ещё поддерживается. Это совместимость со
  старым источником данных, не построение старой многополосной дороги.
  Modern missing event уже не подменяется этим кэшем.

После исправления доставки и идентичности разумно разделить BAPBridge на
выход HUD, выход renderer, расчёт distance/blink и текст/ETA. Сам по себе
перенос таблиц или переписывание всех классов сейчас не исправит найденные
ошибки состояния. Общие правила манёвра и выбора lane event должны остаться
общими для обоих выходов.

Выполнены на указанной ревизии:

- `bash scripts/test_route_info.sh`: PASS, включая 1363 проверки текста,
  1088 манёвров, 1083 сочетания lane angle/status, delta, viewport,

- `bash scripts/test_java_transports.sh`: PASS; реальные локальные сокеты,

- `python3 scripts/check_local_protocols.py`: 38 совпавших Java/C констант;
  107 классов shipping JAR имеют Java 1.4 version 48.0.
- Дополнительный observation probe воспроизводит четыре проблемы выше на
  настоящих классах. Для BAP-ошибки подставлен только HUD endpoint и состояние
  readiness. Для queue pressure writer намеренно не запущен. Для времени
  возраст замера выставлен через reflection без ожидания двух минут.

Это фиксация поведения ревизии, не acceptance-тест: его проверки ожидают

История показывает, что проблема слотов существовала в `42f2cbb0`, ветка

Их нельзя приписывать только последнему добавлению строки полос. Предыдущая
[проверка Java transport](RENDERER_JAVA_TRANSPORT_AUDIT.md) подтверждала

обновлений и повторное использование состояния.
