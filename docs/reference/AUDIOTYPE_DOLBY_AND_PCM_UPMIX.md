# audioType, Dolby Atmos и апмикс обычного PCM

Дата: 2026-09-21. Проект: MHI2 CarPlay.

Документ фиксирует выводы разговора и проверенное состояние исходников.
Апмикс non-buffered PCM здесь описан как возможная доработка, а не уже
реализованная функция.

## Главное

**`audioType` доступен у обычного realtime-потока 100 независимо от наличия
потока 103.** Поэтому выбор обработки медиа можно делать и тогда, когда
iPhone вообще не открывал buffered audio.

**`audioType = media` не означает Dolby Atmos и не гарантирует, что звучит
именно музыка.** Это назначение аудиосессии: там могут быть музыка,
подкаст, аудиокнига, реклама или другие звуки, смешанные самим приложением.

**Для локального HSSR-апмикса нужен стерео PCM, а не обязательно поток 103
или Dolby Atmos.** Наш DSP можно подключить к обычному PCM на магнитоле.

## Три разных признака

| Признак | Что он описывает | Чего из него нельзя заключить |
| --- | --- | --- |
| `streamType` | Вид потока/транспорта: 100 main, 101 alternate, 103 buffered audio | Что в нём каждую секунду звучит и является ли контент Atmos |
| `audioType` | Назначение аудио, например `media`, `telephony`, `alert` | Кодек, число каналов, наличие Atmos или конкретное приложение |
| Формат и число каналов | Как закодирован звук и какой PCM получен после декодирования | Само по себе число каналов не доказывает сохранение Atmos-метаданных |

> ```text
> streamType = 100     // Основной realtime-поток.
> audioType  = media   // Медиа-сессия.
> PCM        = stereo // Два канала после декодирования.
>
> Потока 103 может вообще не быть.
> Этих признаков достаточно для выбора кандидата на локальный апмикс,
> но не для вывода «это Dolby Atmos».
> ```

## Что уже читает наш хук

В `hook/audio/audio_hook.c` функция `spa_stock_main_audio_type()`:

1. Проверяет включение spatial/buffered-функциональности и наличие
   распознанного профиля штатной библиотеки.
2. Читает `streamType` из объекта потока.
3. Для `streamType == 100` читает отдельное поле `audioType`.

Наличие активного 103 не является условием этой функции.
Вызовы `AudioStreamPrepare()` и `AudioStreamStop()` используют результат
для отслеживания основного аудиомаршрута. В нашей интеграции значение
`SPA_DIO_AUDIO_TYPE_MEDIA == 1` соответствует media.

Состояние отслеживается по объектам потока, а не только по последнему
полученному значению: остановка старого media-потока не должна отменить
состояние нового звонка или голосового потока. Это реализовано в
`hook/audio/media_route.h`.

**101 — отдельный alternate-поток.** Указанная функция намеренно принимает
только 100; полного отслеживания назначения 101 она сейчас не реализует.
Нельзя называть любой non-buffered PCM «101».

## Музыка, подсказки, звонки и будильник

| Наблюдение | Практический вывод для обработки |
| --- | --- |
| Подтверждённый main/media/stereo | Кандидат на HSSR-апмикс |
| Телефонный или голосовой маршрут | Пропускать без музыкального апмикса |
| Alternate-поток подсказок/объявлений | Обрабатывать отдельно от музыкального PCM; не включать HSSR автоматически |
| `alert` | Категория сигнала; не доказательство, что это именно будильник |
| `default`, неизвестное назначение или неоднозначная привязка PCM к потоку | Оставлять без апмикса до уточнения назначения |

Если приложение смешало рекламу, речь или сигнал с музыкой внутри одной
media-сессии, эти метаданные не позволяют разделить компоненты смеси.
Кроме того, наличие media-сессии само по себе не означает наличие ненулевых
аудиосэмплов: пауза и тишина — отдельные состояния.

## Dolby Atmos, APAC 5.1 и HSSR

- **Dolby Atmos** относится к формату/представлению исходного контента.
  Поле `audioType` не служит индикатором Atmos.
- **103** означает buffered-транспорт. Он используется как для стерео,
  так и для многоканального аудио; `103 != Atmos`.
- В наших сохранённых автомобильных логах **formatIndex 65 / APAC / 48 кГц /
  6 каналов** подтверждает приём APAC 5.1. Сам этот факт не доказывает
  передачу Atmos-объектов или высотных каналов до усилителя.
- **HSSR** — наш локальный апмикс стерео. Он создаёт многоканальный выход
  из двух каналов; это не декодирование исходного Dolby Atmos и не
  восстановление его оригинальных объектов.

Открытие Apple Music и включение Atmos предшествовало появлению 103
в пользовательском эксперименте. Требование «один раз включить Atmos,
чтобы навсегда разблокировать 103» не подтверждено. Смена приложения,
рендерера и состояния маршрута остаётся отдельным фактором.

## Текущее состояние апмикса и правило (реализовано 2026-09-21)

Buffered stereo проходит через `spa_stereo_upmix_process_s16()` или float-ветку
внутри рендера 103. Обычный realtime PCM в `snd_pcm_plugin_write()` теперь при
`AUDIO_REALTIME_UPMIX=on` идёт через **отдельный** экземпляр того же HSSR-апмиксера
(`spa_rt_upmix` в `audio_hook.c`, свои DSP-состояние и контроллер), а при `off`
или когда правило не выполнено, по-прежнему через `spa_pcm_expand_fallback()`
(L/R + нули). Правило одного периода (`spa_media_route_realtime_upmix_allowed`,
`media_route.h`, тест `tests/media_route_test.c`): период действительно из
realtime-таймлайна (не пауза и не нехватка 103), геометрия 2 → 6, среди
отслеживаемых main-объектов есть media и нет ни одного non-media (звонок, Siri,
alert), апмиксер инициализирован. Инициализация в `snd_pcm_plugin_params`
(модели загружены заранее в `audio_init`), сброс DSP при `prepare` и после любого
не-апмикшенного периода, остановка при закрытии handle. Работает на аудиопотоке
стока: если 4 периода подряд занимают больше 8 мс из 16, апмикс выключается до
закрытия handle (WARN в логе). Простаивающий контроллер уходит в 4-мс сон.
Задержка фронта +10,7 мс (512 кадров HSSR), тыл +12 мс сцены. Alternate 101
и non-media не апмиксятся. **В машину пока не ставилось.**

> ```text
> Предлагаемая политика для новой реализации:
>
> realtime main + audioType=media + stereo PCM 48 kHz
> + достоверная привязка к media-выходу + отсутствие non-media владельца
>     → локальный HSSR, когда realtime действительно владеет выходом;
>
> звонок / голос / alternate / alert / неизвестное назначение
>     → штатное воспроизведение без HSSR;
>
> активный 103
>     → существующая обработка buffered-потока;
>       готовый многоканальный звук повторно не апмиксить.
> ```

Для доработки нужны отдельное состояние DSP для realtime PCM,
заранее подготовленная модель, корректная обработка переключений и
сбросов, а также проверка нагрузки и задержки на магнитоле.
Один общий изменяемый экземпляр DSP для независимых потоков использовать
нельзя. Нельзя подмешивать realtime PCM в паузу или нехватку данных 103,
пока buffered-поток владеет выходом.

## Ограничения Spotify

В проверенных iOS 26.6 / 23G71 и iOS 27 / 24A5418b обнаружены явные
проверки `com.spotify.client` и `com.espn.ScoreCenter`, запрещающие
регистрацию соответствующего FigAirPlay-клиента для buffered audio.
Это не препятствует обработке уже полученного обычного PCM на магнитоле.
Область доказательства — конкретная политика регистрации клиента,
а не все возможные API воспроизведения приложения.

В текстовой выгрузке iOS 26.1 / 23B85 обнаружена аналогичная структура
политики, но аргументы сравнений потеряны; Spotify по ней строго
не подтверждён.
