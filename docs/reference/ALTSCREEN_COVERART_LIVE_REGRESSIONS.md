# altScreen и обложки: регрессии после 13801f2

Проверка 2026-09-12 после развёртывания `a05f774` на Audi MHI2.

Ужесточение парсеров в `13801f2` исключило два формата, которые реально
передаёт iPhone. Первоначальные host-тесты проверяли повреждённые данные,
но не содержали этих допустимых вариантов.

## VideoConfig без тела

В начале потока 111 телефон передавал opcode 1, bodySize 0, flags 0x56.
Парсер avcC возвращал ошибку, и receiver закрывал соединение до первого кадра.
Теперь пакет без тела сохраняет текущие avcC и NAL length size; последующий
непустой пакет по-прежнему должен содержать целые SPS/PPS и помещаться в буфер.

Сверка с локальным Apple receiver:
`Refferences/WirelessCarPlay/source/Sources/AirPlayReceiverSessionScreen.c`,
ветка `kAirPlayScreenOpCode_VideoConfig`: `ScreenStreamSetAVCC` вызывается
только при `bodySize > 0`. Непустой avcC принимается и с ClearScreen: в живом
потоке этот флаг встречался с корректным 40-байтовым avcC. CatPlay отдельно
игнорирует ClearScreen; копировать это поведение для непустого тела не нужно.

После исправления на HU получены avcC, первый IDR и более 1000 кадров;
пользователь подтвердил восстановление altScreen.

## Setup обложки без типа

Наблюдались согласованная file-transfer session 2, корректные контрольные суммы
и непрерывные sequence. Все Setup отвергались до first-data: фактическое тело
Setup имело длину 8 и содержало только uint64 BE размера. Например,
`000000000002251b` означает 140571 байт. Поле uint16 типа отсутствовало.
CatPlay формирует расширенный вариант: размер + тип + необязательные метаданные.
Требовать его для каждого отправителя было ошибкой.

Теперь принимаются size-only Setup (8 байт) и typed Setup (10+ байт).
Неполные размер/тип (0–7 или 9 байт), известные посторонние типы и файлы больше
800000 байт отклоняются. Без типа обязательна сигнатура JPEG/PNG в начале;
длина и first/last data по-прежнему определяют сборку и завершение. Проверки
порядка, контрольных сумм, поколений, ограничений памяти и атомарная публикация
сохранены.

Диагностика пишет только счётчики и метаданные заголовков, максимум 64 записи
на поколение при уровне INFO. Содержимое изображений и control payload не
сохраняется в логах.

## Проверки

- `scripts/run_tests.sh`: PASS; APAC capture integration пропущена без захвата.
- Новый size-only fixture воспроизводит отказ при старом условии Setup.
- Сборка реального EXIF JPEG после size-only Setup, декодирование, PNG 256×256
  и уведомление Java проверены в `coverart_pipeline_test`.
- Парсер обложек и altScreen forwarder прошли AddressSanitizer/UBSan.
- Сборка QNX ARMv7 прошла проверки экспортов, ABI и отсутствия emutls.

На HU после исправления Setup приняты одно- и многопакетные JPEG 28078 и
230971 байт. Оба декодированы из 600×600 и опубликованы как PNG; повторы
той же обложки не вызывали повторной записи. altScreen одновременно перешёл
в VIDEO_ON и принял более 1200 кадров после подключения.
Пользователь подтвердил появление обложки на экране HU. Считанный с HU PNG
256×256 прошёл проверку заголовка и CRC всех блоков.

Установлен hook с SHA256
`a565332a83825754ce86dbfcc366a5ca2cc72f87a2e567ffaa4184992bf48557`.
Рендерер и JAR при этих исправлениях не менялись. В сборке доступны логи;
после проверки временный `/tmp/carplay_verbose` удалён, следующий запуск
использует стандартный порог WARN/ERROR.

Локальные диагностические логи и резервные копии развёртываний лежат в
игнорируемых `local_logs/alt-screen-20260912T152303Z/` и `build/alt-cover-fix-*/`.
