# MIBRoot (MU1316) — CarPlay media routing on internal-amplifier cars

Binary: `MHI2Q_US_AUG22_P5087_MU1316/RE/MIBRoot/MIBRoot` (ARM32 QNX, imagebase 0x100000, PT_LOAD[0] va 0x100000 off 0 fsz 0xf8f754).
Method: IDA (session `mibroot`) for decompiles/xrefs; raw tables, literal pools and the two IDA-undefined
code regions (0x1e1164..0x1e2990 name lookups, 0x1f81cc DEVICETYPE parser) read directly from the ELF and
disassembled with capstone. Read-only; nothing patched. Scratch data: `scratchpad/mibroot_tables/`
(`elf.py`, `srcnames.py`, `resource_table.md`, `connection_table.md`, `src_names.json`).

Every claim is tagged **PROVEN** (bytes/VA in this binary) or **INFERRED**.

> **Binary identity (checked 2026-09-19):** this `RE/MIBRoot/MIBRoot` copy is the RCC MIBRoot
> (`MU1316-…/MIBRoot_RCC` == `rootifs_out/usr/apps/MIBRoot`, sha1 7c86bb56…) with 35 bytes changed by
> earlier experiments: NOP'd branches at VA 0x1e7164/0x1e7173/0x1e7218/0x1e723b (`sub_1E7138`) and small
> edits at 0x7b2974..0x7b8e17 (code IDA leaves undefined). None of them touch the mapper
> (0x1e2a18..0x1e2b18), the connection/resource tables (0xDDEFB8..0xDE0748), the enum lookups or the
> speakerCoding/DEVICETYPE functions analysed below, so every table and VA here holds for the shipped
> RCC image. MIBRoot runs on the **RCC** (TI Jacinto), not on the MMX.

## 0. The mapper (recap, PROVEN)

`sub_1E2A18(conn*, term*, &src, &snk)` (called from `requestRequestConnection` 0x1f1790 @0x1f1900):

```
1e2a1c  LDR R12,=0xDDEFB8          ; connection table, 0x8F=143 records × 20 B  (0xDDEFB8..0xDDFAE4)
1e2a2c..1e2a74  match rec.conn==*conn && rec.term==*term ; R4 = rec.resource (+0xC); 0 → fail
1e2a80  LDR R5,=0xDDFC1C           ; resource table, 0x8F=143 records × 20 B (0xDDFC1C..0xDE0748)
1e2a88..1e2a98  match rec.resource==R4
1e2a9c  LDR R0,=g_externalAmplifierCoded (0x10BC0E8); LDRB
1e2ab8  LDRNE R0,[rec+0xC] / LDREQ R0,[rec+4]     → *src   (ext_src : int_src)
1e2ae8  LDRNE R2,[rec+0x10] / LDREQ R2,[rec+8]    → *snk   (ext_snk : int_snk)
```

Only `g_externalAmplifierCoded` is consulted. xrefs to 0x10BC0E8: reads in 0x1e2a18 (mapper), reads in
0x1e2b18 (reverse mapper src/snk→connection, same byte, same rule), one write at 0x1e6a64
(`AudioPresCtrl_onExternalAmplifierCodedUpdate`, 0x1e6a3c). No other reader.

Selected (src, snk) leave MIBRoot as a DSI call: `sub_1D6CB4` → 0x755a58 = `DMMAudioManagement` proxy
(iface string 0xdb9691), method id 0x80000002, src at msg+0x50, snk at msg+0x54 (PROVEN by disasm).
MIBRoot contains only the DMMAudioManagement **client/proxy** side (strings: `DMMAudioManagementProxy`,
`CDMMAudioManagementClientBase`, `…RequestEvent/ResponseEvent`; no `…Stub`). ⇒ logical-sink → physical
mapping (what sink 31 would do) is NOT in MIBRoot (INFERRED: it is in the DMM audio-manager process).

Caller 0x1fc364 (`[AMMIBClient] setActiveAmplifierCapabilities`): waits for the DMMAudioManagementMIB client
states (+0x188 "connected Amplifier" ==2, +0x1fc "SettingRange" ==2), logs
`DMMAudioManagementMIB::AmplifierInfo(%s)` with the string at client+0x68, parses it with 0x1f81cc, then uses the
enum only for HMI sound-setting capabilities (enum 0x1d → notify SoundShape properties 0xC0000021..23;
`setActiveAmplifierCapabilities(equalizer=%d)`). ⇒ the device type comes from the **DMM AudioManagement
`AmplifierInfo` property** (INFERRED: DMM fills it from the connected amplifier's MOST identification, not from an
EEPROM byte in MIBRoot). It has **no xref into the routing tables or `g_externalAmplifierCoded`**.

### 4.2 "CodedAmplifier" property (AudioDiag) — PROVEN semantics, INFERRED binding
`AudioDiag_onCodedAmplifierUpdate` 0x20a2f4: value 0 → "Amplifier isn't coded correct! please check Byte 11 ;-)",
then 4 virtual dataset-plausibility re-checks; `sub_212B80` etc. wait on it ("Waiting for CodedAmplifierUpdate",
state +236 == 2, value +148 == 1 = INTERN). Its value space {0 invalid, 1 INTERN, 2 EXTERN} is exactly the
Sound_System value published by the E2P handler (§3), so "CodedAmplifier" = **coding byte 11**, not the
DEVICETYPE enum (binding to SPHAudioDiag property 0xC0000011: INFERRED).

### 4.3 External non-B&O amps
For every connection whose resource has distinct columns, the external branch is a fixed record field; there is
no per-device-type remap anywhere on the path 0x1f1790 → 0x1e2a18 → 0x755a58. Connection 162 with
`g_externalAmplifierCoded != 0` **always** yields `eSRC_ENT_AMP_DIO_MEDIA_MC (0x46f) → eSNK_DTCP51 (2)`, for
STANDARD_6CH, BOSE, B&O alike. eSNK_DTCP20 (3) is never produced by any record. Whether a stereo-only external
amp copes with DTCP51 is decided downstream (DMM / amplifier), not in MIBRoot.

## 5. Could the internal branch carry 6 channels? — PROVEN negative in MIBRoot

* No resource record uses `eSNK_SPEAKERS_MC` (31) in either column; no `_MC` source is ever paired with a
  non-DTCP51 sink. The only references to the name are the sink name table (0xDDCFD4) and its string.
* Internal-amp media paths for DVD 5.1 (`eSRC_ENT_AMP_MEDIA_DVD` / `_DVDC_21`), BT, MFP, CLOUD, GAL, A2LS, DIO
  all terminate in `eSNK_SPEAKERS` (1) with the non-`_MC` source.
* There is no speakerCoding == 6CH check (or any other channel-count input) on the routing path; the only
  routing input is the byte at 0x10BC0E8.

Patch plausibility of record 0x78 (@0xDE05A4 bytes +4/+8 → `6f 04 00 00 | 1f 00 00 00`):
* MIBRoot side: mechanically trivial and the mapper would emit (0x46f, 31) to DMM; the name lookups would print
  `eSRC_ENT_AMP_DIO_MEDIA_MC`/`eSNK_SPEAKERS_MC` correctly (both names exist, sink 31 ≤ 0x1f bound at 0x1e11f0).
  Note the reverse mapper 0x1e2b18 uses the same record so it stays consistent.
* Beyond MIBRoot (INFERRED, unverifiable here): the DMM AudioManagement server must have a physical route for
  logical sink 31 with the internal amp, and the source 0x46f must be allocatable without a MOST sink. Nothing in
  this binary shows the internal amp ever being fed >2 channels, so there is no precedent to lean on; whether
  sink 31 is even implemented is a DMM-binary question.
