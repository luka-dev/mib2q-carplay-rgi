# CarPlay → BAP → HUD: проверка сохранения прежнего отображения

Проверка после уточнения пользователя: под «проекцией» имеется в виду **HUD
на лобовом стекле**, получающий BAP, а не OpenGL renderer на Virtual Cockpit.
Исходная ревизия аудита `dda63e4`. После аудита исправлена доставка и
очистка кэша в коммите `9720844` (`origin/master`); повтор матрицы BAP также дал 0 отличий.
Статус исправлений: [Java RGI audit](JAVA_RGI_AUDIT_2026_09_13.md).

## Прежний BAP-выход сохранился

Для актуального BAPBridge исполнен `ManeuverChainAudit`: 7 890 входов, включая
все 54 типа CarPlay, RHT/LHT, углы, боковые дороги и z-level.
Сравнены `mainElement`, `direction`, `zLevelGuidance`, исходный `sideStreets`,
а также результат одинакового stock sender/serializer.

- Сохранённый эталон `output/maneuver-parity/java_mapping.csv`: **0 отличий**.
- Свежая сборка прежнего `BAPBridge.java` из `07e980d`: **0 отличий**.
- ManeuverMapper и SideStreets в обоих прогонах одинаковы: эти файлы не
  менялись после принятой политики иконок `b71ecb9`.

Таким образом, последние изменения движка, заливки и строки полос не
изменили выбор основной HUD-иконки для одинакового корректного входа.
Прежние изменения ramp → slight, полных кругов renderer и конфликтующих
углов остаются отдельными ранее принятыми решениями.

Для полос старый/новый `BAPBridge.sendLaneGuidance` также выполнен на
полноценных данных: каждый угол от −180° до +180°, статусы 0/1/2, дополнительные
направления 0/45/90°. Во всех **1 083 случаях** совпали направление,
guidanceInfo и sideStreets перед передачей штатному BAP sender.

Это сравнение кода и host-пакетов, не новый CAN-захват/прогон оптики HUD.
Реконструированный stock JAR имеет известные артефакты строк; поэтому
отдельно сравниваются реальные числовые поля и byte[] sideStreets на входе
sender. Проверенные ранее HUD selector-ы описаны в
[согласовании манёвров](MANEUVER_RENDERER_PARITY_FIXES.md).

## Где полосы действительно изменились

`git diff 07e980d..dda63e4 -- java_patch/com/luka/carplay/rgd/BAPBridge.java`
показывает изменения на краях допустимых данных:

- При `count=0` старые массивы не восстанавливают исчезнувшие полосы.
- Недоступный современный lane event не подменяется legacy-полосами манёвра.
- Отсутствующие angles одной полосы не берутся от первой полосы.
- Оба sentinel ±1000 и выход за ±180° не превращаются в реальное направление.
- При неизвестном основном угле допустимая запасная ветвь может показываться
  серой, но не получает recommendation из неизвестного primary.
- Изменение route state само по себе пересчитывает разрешение показа полос.

Базовое разрешение `lane_guidance_showing` и независимый активный lane event
сохранены. Здесь нет нового ограничения по типу основного манёвра: полосы
могут отображаться вместе с кругом, поворотом, follow и другими манёврами.

## Исправление слишком широкого вывода предыдущего аудита

В `rgd_parse_maneuver` (`hook/routeguidance/rgd_tlv.c:618–620`) при отсутствии
exit angle для индексированного манёвра устанавливаются **1000 и present-бит**.
`write_slot_data_keys` передаёт это как оба alias `turn_angle/exit_angle`.
Поэтому старый угол не наследуется на штатном входе.

Первоначальный Java-only probe посылал новую версию без этих двух ключей,
обходя существующую защиту. Он доказывал поведение Java при таком delta,
но не доказывал его достижимость от текущего C-producer. Формулировка
[первого аудита](JAVA_RGI_AUDIT_2026_09_13.md) исправлена.

Перепроверка полного пути подтвердила более узкую ошибку: **старые боковые
дороги и прочие отсутствующие поля слота могли наследоваться в `dda63e4`**.
Проверка исполняет настоящий TLV parser, извлечённые без изменений функции
slot writer/text builder, настоящий Java parser и `BAPBridge.sendManeuvers`.
Присвоение slot/version задаёт fixture; сокет и QNX lifecycle не запускаются.

```text
ACTUAL C -> JAVA, missing angle: angle=1000, exit=1000, HUD roads=[]
ACTUAL C -> JAVA, known new angle: angle=90, inherited roads=[-90, 0, 90], road=Old road, step=6000
ACTUAL JAVA -> BAP, same new input: reused-slot sideStreets=[64, 0], fresh-slot sideStreets=[]
```

Очередь CMD_MANEUVER относится только к внешнему renderer на VC и не может
непосредственно потерять FctID 23 HUD. Ошибка повтора после BAP-исключения
относится к обоим выходам; она не означает, что штатный выбор иконки неверен.
Проблема возраста ETA также не является ошибкой выбора стрелки HUD.

## Артефакты и воспроизведение

`output/carplay-projection-crosscheck-2026-09-13/` содержит:

- `hud-packet-comparison.json` — результаты сравнения обоих эталонов;
- `LaneHudMatrix.java`, `lanes-07e980d.tsv`, `lanes-current.tsv` — сравнение
  полноценных lane-записей;
- `crosscheck_native_input.py`, три `*-slot`/`new-*.txt` входа и
  `native-input-result.txt` — проверку sentinel и устаревших дорог.

Старый `crosscheck_native_input.py` — воспроизведение дефекта исходной ревизии;
он намеренно требует наличия ошибки. Для проверки исправленного кода:

```sh
bash scripts/build_java.sh
python3 tests/test_rgd_native_contract.py
```

Полные CSV манёвров и временная сборка прежнего BAPBridge находятся в
`build/carplay-projection-crosscheck/`. Входные штатные проверки Java и
транспорта выполнены в предыдущем проходе на той же production-ревизии.
