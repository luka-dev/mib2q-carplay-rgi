# Как HUD рисует полосы

Проверено 2026-09-13 на оригинальном коде **8W6919617G / 1952** и
**8W6919617M / 2325**. [Картинка с примерами](hud-lanes.png) собрана из
оригинальных спрайтов по результатам исполнения MCU и таблицам GDC.
Это офлайн-реконструкция активной панели, не фотография физической проекции.

## Что видно водителю

- Полосы — самостоятельная горизонтальная строка **под манёвром**.
  HUD не строит из них поверхность дороги и не выводит траектории соединения полос.
- Строка имеет **пять мест**, шаг между ячейками **33 пикселя**.
  Небольшое число полос центрируется; чётное и нечётное число используют разные
  горизонтальные положения, со сдвигом на 16 пикселей.
- В одной ячейке совмещаются **до трёх направлений**. Например, прямо и направо
  образуют одну разветвлённую стрелку, а не две отдельные полосы.
- Между ячейками стоят белые пунктирные разделители. Их включение в исследованном
  пути зависит от количества и положения ячеек, а не от входных типов разметки.
- Если полос больше пяти, видны **четыре настоящие полосы и одно `…`**.
  Многоточие занимает крайнее место, а не добавляется снаружи к пяти стрелкам.

### Цвет выбирается для направления

| `guidanceInfo` | Название в штатном serializer | Основное направление | Дополнительные направления |
|---|---|---|---|
| 0 | NOT_RECOMMENDED_LANE | серое | серые |
| 1 | RECOMMENDED_LANE | серое | серые |
| 2 | BEST_RECOMMENDATION | голубое | серые |

Следовательно, в одной полосе может быть **голубой поворот и серое направление
прямо**. Статус 1 сам по себе не включает голубой спрайт в этих версиях HUD.
Этот результат подтверждён исполнением оригинального MCU, а не только именами
ресурсов. Цвета картинки взяты из извлечённых PNG; яркость физического HUD здесь
не моделируется.

### Как выбирается сторона `…`

При переполнении HUD выбирает левый или правый конец списка:

1. `laneDescription == 5` у первой полосы задаёт правый конец.
2. Иначе `laneDescription == 6` у последней полосы задаёт левый конец.
3. Иначе HUD ищет `guidanceInfo == 2`, сравнивая полосы от обоих краёв внутрь.
   При одинаковом расстоянии сначала проверяется правая сторона.
4. Если основной рекомендации нет, выбирается правый конец.

В штатном `navsd` serializer значения 5/6 называются
`LANE_EXPANDING_TO_LEFT` / `LANE_EXPANDING_TO_RIGHT`. Это признаки расширения,
их нельзя без дополнительной проверки считать достоверным описанием физической
границы дороги. Они имеют приоритет над основной рекомендацией и способны
оставить её за пределами видимой части.

При выборе левого конца показаны первые четыре полосы и `…` справа; при выборе
правого — `…` слева и последние четыре полосы. Двух многоточий одновременно нет.
Окно не перемещается произвольно с центрированием на основной полосе.

## Цепочка оригинального кода

FD51 — V850 little endian, блок загружен по **VA 0x20000**.
В экспортированных `.c` указаны и VA, и смещение в файле.
Контекст MCU: `GP=0xfedff8b4`, `TP=0x28018`, `CTBP=0xb59c0`.

| Функция / таблица | Назначение |
|---|---|
| `0x8ad74`, `0x8ada4` | Сброс модели; установка ёмкости строки 5 |
| [`0x8b21c`](0x8b21c.c) | Получение декодированного BAP snapshot и построение модели полос |
| `0x65b2a`, запись 11 таблицы `0x23f64` | Чтение snapshot из `0xfedfaa02`, 226 байт |
| [`0x8b89c`](0x8b89c.c), `0x8b9a6` | Обрезка невалидных записей только по краям списка |
| [`0x8b9b6`](0x8b9b6.c), [`0x8baa4`](0x8baa4.c), [`0x8bb1c`](0x8bb1c.c) | Центрирование, выбор края, замена крайней ячейки многоточием |
| [`0x8bbe2`](0x8bbe2.c) | Подготовка трёх индексов спрайтов одной ячейки |
| [`0x8bd30`](0x8bd30.c), [`0x8bdc6`](0x8bdc6.c) | Основное и дополнительные направления; только основное со статусом 2 становится голубым |
| `0x8bf8a`, `0x8bfbe` | Проверка кодов направлений по таблицам `0x27dec`, `0x27e11` |
| `0x8bea6`, `0x8bfec`, `0x8c078` | Сортировка направлений, выбор компоновки для двух/трёх стрелок |
| [`0x8c19e`](0x8c19e.c), [`0x8c28c`](0x8c28c.c) | Порядок цветных/серых частей и выбор enum из таблицы `0x3a2e4` |
| [`0x8c2fa`](0x8c2fa.c) | Включение разделителей в чётной/нечётной компоновке |
| [`0x9767a`](0x9767a.c) с аргументом 39 | Перенос модели в display property 7: `0xfedfc708`, 42 байта |
| [`0x95d10`](0x95d10.c) | Проверка доступности панели полос, возврат pane ID 39 |
| [`0x8731c`](0x8731c.c) | Упаковка 35-байтной секции полос, маска группы `1 << 10` |
| FD62 page 3, `0x48ad4`, group bit 10 | 23 элемента выбора готовых поверхностей |

Внутри списка невалидная запись не сдвигает соседние полосы: она сохраняет своё
место. Проверен пример с пустой средней записью. Выключение lane snapshot и
полностью пустой список дают отсутствие поверхностей стрелок и разделителей.

## Направления и спрайты

Исследованный **декодированный кэш** содержит `u16 enabled`, затем восемь
28-байтных записей. Существенные смещения внутри записи:

| Смещение | Поле |
|---|---|
| +0 | valid, для действующей записи 1 |
| +2 | u16 primary direction, 0xff означает отсутствие |
| +4 / +5 / +6 | наличие / длина / данные дополнительных направлений |
| +22 | u16 laneType |
| +24 / +25 | разметка слева / справа |
| +26 | laneDescription |
| +27 | guidanceInfo |

Таблицы распознают коды `00, 20, 40, 60, 72, 92, a0, c0, e0`.
Дополнительные направления добавляются до общего предела три. Используются
заранее подготовленные геометрии `lg_dr`, `lg_2s_dr`, `lg_3s_dr`.
`2s` и `3s` — количество направлений **в одной полосе**. Части `links`, `mitte`,
`rechts`, `kurz`, `lang` обозначают компоновку ветвей внутри ячейки.

Ресурсы: `r0516–r0673` — 158 вариантов стрелок; `r0515` — разделитель 2×32;
`r0675` — многоточие 15×5. Ячейки 1–4 используют u16-селекторы с двумя
горизонтальными вариантами, пятая — компактные u8-селекторы. Состояние 0 пустое.
Суммарные границы объявленных поверхностей полос: **[3,164) × [150,182)**.
Главный манёвр находится в другой группе сцены, bit 2.

В 44-байтной записи поверхности FD62 координаты идут как **x на +30, y на +32**,
затем ширина и высота. В старых внешних заметках эти подписи местами перепутаны.

### Исправление прежней трактовки

`LaneGuidanceWrapper.java` на MCU HUD: подсчёт битов `laneDirection/laneType`

Здесь выбирается основное направление и отдельный список дополнительных;
`laneType` не используется как битовая маска дополнительных стрелок. Есть особая
ветка для типа 8, который в штатном serializer называется BUS_LANE; полный

## Проверка и воспроизведение

1. `tools/ghidra/HudLaneChainAudit.java` исполняет оригинальный V850 от готового
   кэша до display packet. **31 сценарий на каждой прошивке, 369370 инструкций
   на версию, 0 подменённых функций**. Перед каждым сценарием очищаются RAM и
   регистры; pane 39 задаётся явно, чтобы изолировать отображение полос.
2. `tools/verify_hud_lane_graphics.py` исполняет оригинальный ARM dispatcher GDC.
   **4300 проверок состояний на каждой прошивке**: все объявленные состояния
   23 элементов и контрольные пустые/недопустимые состояния. Подменяются только
   границы отправки и учёта готовой поверхности; сравниваются её исходные 44 байта.
3. `tools/build_hud_lane_examples.py` сверяет результаты версий, проверяет
   цвета/переполнение/пустые состояния и составляет картинку из исходных PNG.

Данные: [входы](lane-inputs.csv), [MCU G](lane-G.csv), [MCU M](lane-M.csv),
[полученные поверхности](lane-results.json). Во всех проверенных сценариях
результаты двух прошивок совпадают; совпадают и таблицы элементов группы полос.

Команды из корня репозитория; используются локальные Ghidra, Python, Unicorn и Pillow:

```sh
HUD_ROOT=/Users/luka/Desktop/AUDI_2/Firmwares/HUD/extracted
HUD_G="$HUD_ROOT/FL_8W6919617G_1952_APPL_V000"
HUD_M="$HUD_ROOT/FL_8W6919617M_2325_APPL_V000"
HUD_OUT=output/r2/hud-lanes-2026-09-13
HUD_HEADLESS=/opt/homebrew/opt/ghidra/libexec/support/analyzeHeadless
mkdir -p build/hud-lanes/reproduce
"$HUD_HEADLESS" build/hud-lanes/reproduce HudLaneCheck \
  -import "$HUD_G/blocks/FD_51FLASHDATA.bin" \
  -processor V850:LE:32:default -loader BinaryLoader -loader-baseAddr 0x20000 \
  -noanalysis -scriptPath tools/ghidra \
  -postScript HudLaneChainAudit.java "$HUD_OUT/lane-inputs.csv" "$HUD_OUT/lane-G.csv" \
  -postScript HudLaneChainAudit.java "$HUD_OUT/lane-inputs.csv" "$HUD_OUT/lane-M.csv" "$HUD_M/blocks/FD_51FLASHDATA.bin"
python3 tools/verify_hud_lane_graphics.py "$HUD_G" "$HUD_OUT"
python3 tools/verify_hud_lane_graphics.py "$HUD_M" "$HUD_OUT"
python3 tools/build_hud_lane_examples.py
```

Для первого запуска нужен новый проект `HudLaneCheck`; при повторном используйте
`-process FD_51FLASHDATA.bin` вместо `-import` и параметров загрузчика.
Ghidra может вернуть exit 0 при ошибке скрипта: необходимы две строки
`HUD_LANE_CHAIN_PASS`, отсутствие `ERROR` и успешная проверка compositor.

Хеши FD61/FD62 сохранены в двух `*-lane-selectors.json`.

`138351c2f12cd8e45d9f50fd4833775371ec46401b6838f04c24a9a4baaabae2`.

`6e59b62c982873a778bf72b749bf6dc113fe3fe14ee4bb3ae3855d0c624f6fe5`.

Границы проверки: не моделируются физическая оптика, весь арбитраж панелей HUD,
