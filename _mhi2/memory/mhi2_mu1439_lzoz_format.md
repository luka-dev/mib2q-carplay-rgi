## ✅ SOLVED (2026-05-26) — MU1439-lsd.jar PRODUCED (123 MB, 28,528 classes) at `Tools/jxe2jar/out/MU1439-lsd.jar`. Clean imagefs at `extracted/mifs-stage2.full.imagefs` (76,036,904 B, validated by QNX dumpifs).
**Correct format (ALL my stage1/dict-hunt notes below were a RED HERRING):**
- Algorithm = **lzo1z** (NOT lzo1x). "LZOZ" magic ↔ stage1 string "found lzo1z header". Use genuine QNX `liblzo.a` `lzo1z_decompress_*` (on the QNX VM).
- The 37 table entries (@ file 0x8.., compressed lengths) are **37 INDEPENDENT lzo1z streams**, each decompressing to exactly 0x200000 (last = remainder). NOT one continuous stream.
- Blocks are **512-byte aligned** in the file: `fb[k+1] = fb[k] + ((tbl[k]+0x1ff) & ~0x1ff)`, fb[0]=0x800. (This is the only "framing fix" — there was no real "block-36 desync"; that was an artifact of the wrong lzo1x decoder.)
- **Preset dict for blocks 1–36 = block 0's OWN decompressed output** (0x200000 bytes), via `lzo1z_decompress_dict_safe(src,srclen,dst,&dlen, wrk, dict=block0, dict_len=0x200000)`. Block 0 uses plain `lzo1z_decompress_safe`. NO external/stage1 dictionary.
- lsd.jxe is NOT nested — directly at `ifs/lsd.jxe` in the imagefs (offset 0x878000, ~58 MB, PK/ZIP-style jxe). dumpifs or carve-by-offset → jxe2jar.py → jar.
- Working VM decoder was `/tmp/vmfinal.c`. The macOS lzo1x tooling under `extracted/` is superseded — ignore it.
